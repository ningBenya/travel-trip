# ระบบ login · หน้าปฏิทิน · สมาชิกทริป — design

วันที่ 24 พ.ย. 2026 · branch `feat/login-members` (แยกจาก `ux/safer-easier-screens`)

## ทำไมต้องทำ
ตอนนี้ใครที่มีลิงก์เว็บ หรือรู้ที่อยู่ฐานข้อมูลจาก `firebase-config.js` ก็อ่าน แก้ และลบได้ทุกทริป
เจ้าของอยากให้แต่ละคนเห็นและแก้ได้เฉพาะทริปของตัวเอง โดยมี admin เป็นคนสร้างบัญชีให้ทุกคน

## เป้าหมาย
1. ต้อง login ก่อนใช้งาน ด้วย username + รหัสผ่าน
2. หลัง login หน้าแรกเป็นปฏิทินรายเดือน มีแถบแสดงช่วงวันไป–วันกลับของแต่ละทริป และกดแถบเพื่อเปิดทริปได้
3. ในแต่ละทริปเพิ่มหรือเอาคนออกได้ โดยเลือกจากรายชื่อผู้ใช้ในระบบ
4. แต่ละคนอ่านและแก้ได้เฉพาะทริปที่ตัวเองเป็นสมาชิก โดยบังคับด้วยกฎของ Firebase จริง ไม่ใช่แค่ซ่อนบนหน้าจอ
5. บัญชี admin `hwangning` เห็นและแก้ได้ทุกทริป และจัดการผู้ใช้ได้
6. มีหน้าเปลี่ยนรหัสผ่านของตัวเอง

## ไม่ทำ
- ไม่มีหน้าสมัครสมาชิกเอง (admin เป็นคนสร้างบัญชีให้)
- ไม่ย้ายออกจาก Firebase หรือ GitHub Pages
- ไม่ทำบทบาทย่อยอย่าง "ดูได้อย่างเดียว" (สมาชิกทุกคนแก้ได้)

## สิ่งที่ถือว่าล้มเหลว แม้ระบบจะทำงานได้
- คนที่ไม่ได้ login หรือไม่ได้เป็นสมาชิก ยังดึงข้อมูลทริปได้ด้วยการเรียกฐานข้อมูลตรง ๆ
- รหัสผ่านไปอยู่ในโค้ด ใน repo หรือในฐานข้อมูล
- ทริปและรูปเดิมหายหลังอัปเดต

## ข้อจำกัด
- โฮสต์แบบ static บน GitHub Pages: ไม่มี server และไม่มี Admin SDK
- ใช้ Firebase Realtime Database ตัวเดิม (`travel-ddcbc`) ข้อมูลอยู่ใต้ `planner/`
- ใช้ JS แบบ vanilla และ Firebase compat SDK 10.12.2 ต่อไป (เพิ่ม `firebase-auth-compat.js`)
- ตอนนี้แอปโหลดทั้ง `planner/trips` และ `planner/items` ในครั้งเดียว ต้องเปลี่ยนเป็นโหลดทีละทริป

## วิธีที่พิจารณา (เลือก A)
- **A. Firebase Authentication + กฎฐานข้อมูลใหม่** ← เลือกแบบนี้: ฟรี ไม่ต้องย้ายข้อมูล และ Firebase บังคับสิทธิ์ให้จริง
- B. SQLite + server ของตัวเอง: เปิดไฟล์ใน DB Browser ได้ แต่ต้องเช่าและดูแล server เขียนส่วนข้อมูลใหม่ทั้งหมด และย้ายข้อมูลกับรูป
- C. SQLite ในเบราว์เซอร์: ตัดทิ้ง เพราะแต่ละเครื่องได้ข้อมูลแยกกัน แชร์ไม่ได้ และไฟล์ที่ฝากบน GitHub ใครก็ดาวน์โหลดได้

## การออกแบบ

### บัญชีผู้ใช้
- Firebase Auth แบบ Email/Password บังคับให้ใช้อีเมล จึงแปลง username เป็นอีเมลภายใน `<username>@travel.local`
  ผู้ใช้พิมพ์แค่ username ไม่เห็นอีเมลนี้
- username: ตัวอักษร a–z ตัวเลข `.` `_` `-` ยาว 3–30 ตัว เก็บเป็นตัวพิมพ์เล็ก
- admin ดูจากอีเมลใน token: `auth.token.email === 'hwangning@travel.local'`
  ทำให้ไม่ต้องแก้ฐานข้อมูลเองตอนเริ่มต้น
- โปรไฟล์ผู้ใช้อยู่ที่ `planner/users/{uid}` = `{ username, name, createdAt }`
  **ต้องมีโปรไฟล์ถึงจะเข้าถึงข้อมูลได้** คนที่สมัครเองผ่าน API จึงไม่ได้สิทธิ์อะไร และการลบโปรไฟล์ = ปิดบัญชี
- `planner/usernames/{username}` = uid ไว้กัน username ซ้ำ
- admin สร้างผู้ใช้ในแอปผ่าน **Firebase app instance ตัวที่สอง** (`createUserWithEmailAndPassword`)
  เพื่อไม่ให้ session ของ admin หลุด จากนั้นเขียนโปรไฟล์และ username แล้วออกจาก instance ตัวที่สอง
- admin ตั้งรหัสเริ่มต้นให้ และผู้ใช้เปลี่ยนเองในหน้าเปลี่ยนรหัสผ่าน

### ข้อมูลทริปและสิทธิ์
- `planner/trips/{tripId}` เพิ่ม `ownerId` และ `members: { uid: true }` (เจ้าของอยู่ใน members ด้วย)
- `planner/userTrips/{uid}/{tripId}: true` เป็นดัชนีว่าแต่ละคนอยู่ทริปไหน
  จำเป็นเพราะกฎของ Realtime Database ไม่กรองรายการให้ ถ้าไม่มีสิทธิ์อ่านทั้งก้อน `trips` ก็อ่านไม่ได้ทั้งหมด
- การโหลด: ผู้ใช้ทั่วไปฟัง `userTrips/{me}` แล้วฟัง `trips/{id}` กับ `items/{id}` ทีละทริป
  admin ฟัง `trips` และ `items` ทั้งก้อนเหมือนเดิม
- ใครทำอะไรได้ (my call):
  - สมาชิก: อ่านและแก้รายละเอียดทริป รายการ และแผนรายวัน
  - เจ้าของ + admin: เพิ่มหรือเอาสมาชิกออก และลบทริป
  - สมาชิกกด "ออกจากทริป" ได้ แต่เจ้าของออกไม่ได้
- รูป (`photos`, `thumbs`): อ่านและเขียนได้เฉพาะผู้ใช้ที่มีโปรไฟล์ (id เป็นสุ่มยาว เดาไม่ได้)
  ไม่ผูกกับทริปเพราะต้องรื้อโครงสร้างรูปทั้งหมด (my call)
- `planner/users` อ่านได้ทุกคนที่ login แล้ว (ต้องใช้เลือกคนเข้าทริป) แต่เขียนได้เฉพาะ admin
  ยกเว้นช่อง `name` ของตัวเอง

### กฎฐานข้อมูล (โครง)
```
isUser  = auth != null && root.child('planner/users/' + auth.uid).exists()
isAdmin = auth != null && auth.token.email == 'hwangning@travel.local'
member(t) = root.child('planner/trips/' + t + '/members/' + auth.uid).exists()

trips/$t   .read:  isAdmin || member($t)
           .write: isAdmin || (isUser && (member($t) || (!data.exists() && newData.child('ownerId').val() == auth.uid)))
           ownerId และ members แก้ได้เฉพาะเจ้าของหรือ admin ยกเว้นตอนสร้างทริป
           ลบทริป (newData ว่าง): เจ้าของหรือ admin
items/$t   .read/.write: isAdmin || member($t)
userTrips/$u .read: auth.uid == $u || isAdmin
userTrips/$u/$t .write: isAdmin || เจ้าของทริป $t || ($u == auth.uid && newData ว่าง)
           (สำหรับ multi-path update ใช้ newData.parent()... เพื่อตรวจสถานะหลังอัปเดต)
users      .read: isUser || isAdmin ; users/$u .write: isAdmin ; users/$u/name .write: $u == auth.uid
usernames  .read: isUser || isAdmin ; .write: isAdmin
photos, thumbs .read/.write: isUser || isAdmin (คง validate ขนาดและชนิดเดิม)
```
การเขียนทุกครั้งยังผ่าน `commit()` ซึ่งยิง `update()` ที่ `planner/` เพียงครั้งเดียว
Firebase เช็กกฎทีละ path ให้เอง

### ข้อมูลเดิม
- ทริปเดิมไม่มี `members` จึงเห็นได้เฉพาะ admin (ผ่าน `isAdmin`) จนกว่า admin จะเปิดทริปแล้วเพิ่มคน
- ครั้งแรกที่ admin login แอปจะเติม `ownerId` = admin และ `members.{admin}` ให้ทริปที่ยังไม่มีเจ้าของ
  ข้อมูลเดิมไม่หาย

### หน้าจอ
- **หน้า login:** ช่อง username กับรหัสผ่าน ปุ่ม "เข้าสู่ระบบ" และข้อความผิดพลาดภาษาไทย ("username หรือรหัสผ่านไม่ถูกต้อง", "ลองผิดหลายครั้ง รอสักครู่")
  หลัง login แล้วจะจำไว้จนกว่าจะกดออกจากระบบ
- **โครงหลัก:** แถบด้านข้างหรือแถบบนมีเมนู "ปฏิทิน" "ทริป" และเมนูผู้ใช้ (ชื่อผู้ใช้ → เปลี่ยนรหัสผ่าน · จัดการผู้ใช้ (เฉพาะ admin) · ออกจากระบบ)
- **ปฏิทิน (หน้าแรก):** ตารางเดือนแบบจันทร์–อาทิตย์ ปุ่มเดือนก่อน/ถัดไป/วันนี้
  แต่ละทริปเป็นแถบสีตามธีมของทริป ยาวตามช่วงวัน ถ้าข้ามสัปดาห์จะตัดเป็นหลายแถบ ทริปซ้อนวันกันเรียงเป็นหลายชั้น
  บนมือถือเป็นตารางย่อ แล้วแสดงรายการทริปของเดือนอยู่ด้านล่าง
  ทริปที่ไม่มีวันที่ไปอยู่ในรายการ "ยังไม่ระบุวัน" และเปิดเดือนแรกที่เดือนปัจจุบัน
  ```
  ‹  ธันวาคม 2569  ›            [วันนี้]
  จ   อ   พ   พฤ  ศ   ส   อา
  8   9   10  11  12  13  14
          ███ เชียงใหม่ ███
  ```
- **สมาชิกทริป:** ในหน้าทริป (ในกล่องแก้ไขทริป หรือแถบ "สมาชิก") แสดงชื่อสมาชิกเป็นรายการ
  เจ้าของหรือ admin มีช่องค้นหาจากรายชื่อผู้ใช้ มีปุ่ม "เพิ่ม" และปุ่ม "เอาออก" ที่กด "เลิกทำ" ได้
- **เปลี่ยนรหัสผ่าน:** กรอกรหัสเดิม รหัสใหม่ (อย่างน้อย 8 ตัว) และยืนยันรหัสใหม่
  ใช้ `reauthenticateWithCredential` แล้ว `updatePassword`
- **จัดการผู้ใช้ (admin):** รายชื่อผู้ใช้ ฟอร์ม "สร้างผู้ใช้" (username, ชื่อที่แสดง, รหัสเริ่มต้น) และปุ่ม "ปิดบัญชี" (ลบโปรไฟล์ เอาออกจากทุกทริป และลบ username)
- โหมดไม่มี Firebase (เก็บในเครื่อง): ไม่ต้อง login แบบเดิม ไว้ทดสอบ (my call)

### สิ่งที่เจ้าของต้องทำเองใน Firebase Console
1. Authentication → Get started → Sign-in method → เปิด **Email/Password**
2. Authentication → Users → Add user: อีเมล `hwangning@travel.local` และรหัสผ่านที่ต้องการ
3. หลัง merge โค้ดใหม่ขึ้น GitHub Pages แล้ว: Realtime Database → Rules → วางกฎใหม่จาก `database.rules.json` → Publish
   (ต้องทำหลังโค้ดขึ้นแล้ว เพราะเว็บเวอร์ชันเก่าใช้กับกฎใหม่ไม่ได้)
4. ครั้งแรกที่ `hwangning` login แอปจะสร้างโปรไฟล์ admin ให้เอง

## ข้อจำกัดที่ต้องรู้
- **ลืมรหัสผ่าน:** อีเมล `@travel.local` รับอีเมลรีเซ็ตไม่ได้ และแอปที่ไม่มี server ตั้งรหัสใหม่ให้คนอื่นไม่ได้
  ทางแก้คือ admin ลบบัญชีนั้นใน Firebase Console (Authentication → Users) แล้วสร้างใหม่ด้วย username เดิมในแอป
  แอปจะผูก uid ใหม่เข้ากับทริปเดิมให้ ถ้าเลือกตอนสร้างว่า "แทนบัญชีเดิม"
- ปุ่ม "ปิดบัญชี" ในแอปตัดสิทธิ์ได้ทันที แต่บัญชีใน Firebase Auth ยังอยู่จนกว่าจะลบใน Console

## เหลือให้ผู้สร้างตัดสินใจเอง
- หน้าตาและตำแหน่งของเมนู ให้เข้ากับ visual เดิม (Plex Thai, พื้นครีม, สีธีมทริป)
- การ route ภายในหน้าเดียว (`#calendar`, `#trip=<id>`, `#account`, `#users`) โดยให้ลิงก์ `#trip=<id>` เดิมยังใช้ได้หลัง login
- ข้อความ error ภาษาไทยของแต่ละรหัสข้อผิดพลาดจาก Firebase Auth
